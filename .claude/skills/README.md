# Skills

Los **skills** son conocimiento empaquetado que Claude Code carga **on-demand** (solo cuando hace falta, sin pesar en el contexto si no se usan). Sirven para encapsular el "cómo" de una capacidad reutilizable que varios agentes pueden aprovechar.

## Skills disponibles

- **`tecnicas-de-diseno/`** — técnicas formales de diseño de casos de caja negra (clases de equivalencia, valores límite, tabla de decisión, transición de estados, pairwise). Sirve para derivar casos más completos al generar pruebas manuales, BDD o de API.
- **`ejecucion-e2e/`** — cómo ejecutar pruebas E2E en el navegador con Playwright MCP (modo headed/headless, ubicar elementos por accesibilidad, esperas para evitar flakiness, evidencia). Lo usa el agente `ejecutor-e2e`.
- **`ejecucion-api/`** — cómo ejecutar pruebas de API con Newman (la CLI de Postman): correr una colección, escribir validaciones, manejar base_url y token, e interpretar los resultados. Lo usa el agente `ejecutor-api`.
- **`pruebas-accesibilidad/`** — cómo auditar accesibilidad (a11y) en web (WCAG 2.2, axe-core, teclado, contraste, ARIA, lectores de pantalla), mobile (TalkBack/VoiceOver, etiquetas accesibles, objetivos táctiles, escalado de fuente) y desktop (UI Automation, controles sin nombre accesible, teclado, alto contraste), con el mapeo de WCAG a cada plataforma. Lo usa el `analista-accesibilidad` y lo referencian el `probador-mobile` y el `probador-desktop`.
- **`investigacion-contexto/`** — cómo investigar a fondo una historia antes de trabajarla (primero la documentación del proyecto de `input/documentacion/` que arma el `documentador-proyecto`; después Jira con comentarios, subtareas, épica e issues vinculados; Confluence; Figma; contratos; `input/`) y cómo registrar lo que falta como **Falta información** (`FI-XX`) en la ficha `output/contexto/contexto-HU-XXX.md`. Lo usan el analista, el estratega, los generadores de casos, los mappers y el `documentador-proyecto`.
- **`guia-pruebas/`** — asistente interactivo que guía a la persona para elegir qué probar y con qué agente o skill: pregunta paso a paso, ramifica según las respuestas y recomienda o ejecuta; incluye el mapa de plataforma y tipo de prueba hacia el agente/skill que corresponde. Lo usa la conversación principal (los subagentes no pueden preguntar), igual que `guia-performance`.
- **`base-conocimiento/`** — flujo de la conversación principal para armar y mantener la base de conocimiento de **todo** el proyecto en `input/documentacion/` (investigador en profundidad total, documentador en modo barrido y con la app recorrida de punta a punta con sesión, manuales), usarla para escribir y automatizar casos, y mantenerla al día cuando cambian los requerimientos (historias, código y aplicación).
- **`guia-performance/`** — guía paso a paso para planificar una prueba de performance con la persona (tipo de prueba, herramienta, ambiente, usuarios, rampa, duración, tiempo de pensamiento y umbrales, con sugerencias y cálculos) y dejar el plan confirmado para el `performance-mapper`. Lo usa la conversación principal, porque los subagentes no pueden hacerle preguntas a la persona.
- **`relevamiento-proyecto/`** — cómo relevar un proyecto **entero** por MCP (Jira, Azure DevOps, Confluence, repo, Figma): barrer cada herramienta con consultas acotadas, muestrear backlogs grandes, extraer módulos, flujos, integraciones y equipo, y clasificar ambigüedades, contradicciones y vacíos en preguntas priorizadas. Lo usa el `investigador-proyecto`.
- **`redaccion-manual/`** — cómo crear o actualizar manuales de usuario basados en evidencia (de una funcionalidad o de toda la plataforma): fuentes del proyecto y la app con Playwright MCP, matriz de evidencia, gaps, acciones prohibidas, capturas, QA REVIEW, aprobación y checklist, y el conocimiento que queda en `input/documentacion/manual-usuario/` para los casos. Sirve para cualquier tipo de proyecto. Lo usa el `redactor-manual`.
- **`pruebas-salesforce/`** — cómo probar una org de Salesforce: ambientes y sandboxes, acceso (perfiles, permission sets, OWD, FLS), automatización (validaciones, flows, triggers, orden de ejecución, límites de gobierno, bulk de 200), datos (record types, picklists, duplicados), Lightning con Playwright, APIs, tests de Apex y releases. Lo usa el `probador-salesforce`.
- **`pruebas-tokens/`** — cómo probar tokens de autenticación (JWT, OAuth 2.0/OIDC, sesión, API keys) y la tokenización de tarjetas (PCI): ciclo de vida, firma y claims, ataques típicos (alg none, replay, scope), manejo seguro y qué no hacer con datos reales. Lo usan el `probador-billeteras`, el `probador-salesforce` y el `pentester-web`.
- **`pruebas-billeteras/`** — cómo probar billeteras virtuales y pagos: saldo y libro mayor (conservación del dinero), transacciones y estados, idempotencia y reintentos, doble gasto y concurrencia, redondeo y moneda, límites, KYC/AML, conciliación con la pasarela y webhooks. Lo usa el `probador-billeteras`.
- **`pruebas-ecommerce/`** — cómo probar cualquier tienda online: catálogo, variantes, precios y redondeo, stock y sobreventa, carrito, checkout, impuestos, envíos, cupones, pagos en modo de prueba, posventa, correos, multi-moneda, mobile, SEO y legales; qué agente cubre cada parte y los bugs típicos. Lo usan el `probador-shopify` y el `probador-wordpress`.
- **`pruebas-shopify/`** — cómo probar una tienda Shopify: tiendas de desarrollo, temas y Theme Check, errores de Liquid, apps, checkout con Bogus Gateway o modo de prueba, Markets, envíos y ubicaciones, descuentos, webhooks con HMAC, Admin API de solo lectura y automatización con Playwright. Lo usa el `probador-shopify`.
- **`pruebas-wordpress/`** — cómo probar WordPress y WooCommerce: plugins y temas (actualizaciones, templates sobrescritos), caché, WP-Cron, REST y Store API, checkout clásico o de bloques, pasarelas en modo de prueba, envíos, impuestos, cupones, stock, estados del pedido, correos, webhooks y roles. Lo usa el `probador-wordpress`.
- **`pruebas-prestashop/`** — cómo probar PrestaShop (1.6, 1.7, 8.x): ambientes y smoke local con Docker, BO/FO, temas y plantillas Smarty, módulos y overrides, caché y rendimiento (Smarty, CCC, modo desarrollador), checkout (invitado, transportistas, términos), pagos de prueba, combinaciones y stock, impuestos y redondeo, multitienda, multi-idioma, correos y la Webservice API de solo lectura. Lo usa el `probador-prestashop`.
- **`pruebas-vtex/`** — cómo probar VTEX: cuentas, entornos y workspaces (master vs. QA), storefront (Store Framework, FastStore, legacy) y apps de VTEX IO, Catalog System y trade policies, pricing, logistics y SLAs, promociones, pagos y antifraude, el checkout y el orderForm, OMS y marketplace, smoke, regresión, rendimiento, seguridad y las APIs de solo lectura. Lo usa el `probador-vtex`.
- **`pruebas-sap/`** — cómo probar SAP (S/4HANA o ECC): SAP GUI (T-codes, Scripting API por COM) y Fiori/UI5 (launchpad, OData), mandantes y transportes, autorizaciones y roles (PFCG, SU01, SU53, SoD), procesos de negocio de punta a punta (O2C, P2P, R2R), datos maestros, jobs e IDocs, smoke, regresión tras un transporte, rendimiento (ST03/ST05) y seguridad. Lo usa el `probador-sap`.
- **`pruebas-desktop/`** — cómo probar apps de escritorio de Windows (WinForms, WPF, UWP, Win32, Electron, Java, Qt) y su herramienta (Appium + WinAppDriver, pywinauto, Playwright para Electron): árbol de controles y localizadores, funcional (ventanas, menús, formularios, teclado), instalación y actualización, archivos, integración con el SO (registro, DPI, multi-monitor), smoke, regresión, rendimiento, seguridad y accesibilidad. Lo usa el `probador-desktop`.
- **`pruebas-mobile/`** — cómo probar apps móviles (Android/iOS; nativa, híbrida o web/PWA): dispositivos y matriz de OS, instalación/distribución, permisos del sistema, interrupciones, conectividad (offline, red lenta), deep links y push, ciclo de vida (segundo plano, rotación, matar/relanzar), rendimiento, seguridad móvil (MASVS) y accesibilidad; automatizar con Appium. Lo usan el `probador-mobile` y el `mobile-mapper`.
- **`analisis-dependencias/`** — cómo analizar la seguridad de las dependencias (SCA): ecosistemas y lockfiles, CVE/CVSS, directas vs. transitivas, reachability, licencias, SBOM, cadena de suministro (dependency confusion, typosquatting) y riesgo aceptado; npm audit, pip-audit, osv-scanner. Lo usa el `analista-dependencias`.
- **`revision-codigo/`** — cómo hacer una revisión estática de código (code review): traer el código de GitHub, GitLab, Bitbucket, Azure Repos o cualquier git sin ejecutarlo, revisar un PR/MR contra el merge-base, qué mirar por categoría (seguridad, performance, confiabilidad, malas prácticas, mantenibilidad) y lenguaje, umbrales, severidad y decisión, triage de falsos positivos y comentarios útiles. Lo usa el `revisor-codigo`.
- **`codigo-seguro/`** — cómo hacer SAST y búsqueda de secretos: clases de bug (inyección, XSS, deserialización, SSRF, cripto…) mapeadas a OWASP/CWE, semgrep, triage de falsos positivos, detección de secretos y su rotación, y la diferencia entre SAST y DAST. Lo usa el `analista-codigo-seguro`.
- **`pruebas-ia/`** — cómo probar funciones de IA/LLM (chatbot, RAG, clasificador, agente): golden set y evals, alucinaciones y grounding/citas, seguridad de prompt (injection directo e indirecto, jailbreak, fuga de PII), formato de salida, robustez, límites, latencia/costo, privacidad y regresión de prompts. Lo usa el `probador-ia`.
- **`pruebas-async/`** — cómo probar mensajería y eventos (asíncrono / event-driven): brokers y protocolos (Kafka, RabbitMQ/AMQP, SQS/SNS, MQTT, WebSocket, SSE), entrega (at-least-once/exactly-once), orden por clave/partición, idempotencia y deduplicación, reintentos y DLQ, esquemas y compatibilidad (Avro/JSON Schema), consumer lag y contrapresión, patrón outbox y seguridad. Lo usa el `probador-mensajeria`.
- **`pruebas-graphql/`** — cómo probar APIs GraphQL: schema e introspección, queries/mutations/subscriptions con variables y fragments, errores parciales y nulabilidad (data + errors con HTTP 200), autorización por campo/tipo, N+1, límites de profundidad y complejidad, paginación (cursor/offset) y persisted queries. La usan el `ejecutor-api`, el `api-mapper` y el `generador-casos-api`.
- **`pruebas-soap/`** — cómo probar servicios SOAP: WSDL (operaciones, endpoint, bindings), sobre (Envelope/Header/Body), SOAP 1.1/1.2, validación contra el XSD, SOAP Faults, namespaces y SOAPAction, WS-Security (UsernameToken, firma, timestamp), mustUnderstand, tipos y arrays, idempotencia y versionado del contrato. Lo usa el `probador-soap`.
- **`pruebas-scalar/`** — cómo probar APIs que están en Scalar: el server MCP de la API (Search/Execute, créditos), el Registry, los casos como colección con tests `pm` que corre con Newman y la importación a Scalar (ejemplos por caso y `x-post-response`, publicando con confirmación). Lo usa el `probador-scalar`.
- **`pruebas-grpc/`** — cómo probar gRPC y APIs de tiempo real: Protocol Buffers (.proto, campos y números), los cuatro modos de RPC, status codes de gRPC, metadata, deadlines y cancelación, TLS/mTLS, compatibilidad de Protobuf y gRPC-Web; WebSocket se cubre en `pruebas-async`. La usan el `ejecutor-api`, el `api-mapper` y el `generador-casos-api`.
- **`pruebas-contratos/`** — cómo hacer contract testing: contratos consumer-driven (Pact) y por proveedor, el Pact Broker y can-i-deploy, matchers por tipo y provider states, compatibilidad hacia atrás/adelante, y contratos para REST, GraphQL, gRPC y mensajería. Lo usa el `probador-contratos`.
- **`pruebas-seo/`** — cómo probar el SEO y el GEO: SEO técnico (indexabilidad, robots/sitemap, canónicas, redirecciones, hreflang), on-page, datos estructurados (JSON-LD, Open Graph), Core Web Vitals, y GEO (acceso de crawlers de IA, contenido citable, E-E-A-T, llms.txt). Lo usa el `analista-seo`.
- **`pruebas-datos/`** — cómo probar datos y pipelines (ETL): dimensiones de calidad, reconciliación origen↔destino, validación de esquema y drift, transformaciones y SCD, idempotencia y cargas incrementales, late data, PII y linaje. Lo usa el `probador-datos`.
- **`pruebas-dynamics/`** — cómo probar Dynamics 365 y otros CRM/ERP de bajo código: entornos y soluciones, seguridad (roles, unidades de negocio, column security), modelo de datos de Dataverse, lógica (business rules, flows, plugins, BPF, roll-ups), apps, Web API y procesos end-to-end. Lo usa el `probador-dynamics`.
- **`pruebas-blockchain/`** — cómo probar blockchain/Web3 y smart contracts: redes y entornos (testnet/local/fork), funcional del contrato, tokens (ERC-20/721/1155), gas, seguridad (reentrancy, control de acceso, oráculos, proxies), firmas (EIP-712) e integración dApp con Hardhat/Foundry. Lo usa el `probador-blockchain`.
- **`pruebas-ivr/`** — cómo probar voz/IVR y voicebots: árbol de menús (DTMF/ASR), prompts y TTS, flujo y manejo de errores, enrutamiento y colas, transferencias y CTI, telefonía (SIP/VoIP, audio, DTMF), grabación y cumplimiento (PCI) y voicebots con NLU/LLM. Lo usa el `probador-ivr`.
- **`pruebas-juegos/`** — cómo probar videojuegos: funcional (mecánicas, progresión, físicas, controles), compatibilidad y rendimiento, guardado y persistencia, multijugador y red (anti-cheat), economía/monetización, audio/localización/accesibilidad y exploratorias para romper el mundo. Lo usa el `probador-juegos`.
- **`pruebas-pos/`** — cómo probar punto de venta (POS) y hardware: flujo de venta y arqueo, medios de pago y pinpad, periféricos (impresora, cajón, balanza, lector), integración fiscal, modo offline y sincronización, inventario, roles y conciliación de caja. Lo usa el `probador-pos`.
- **`pruebas-observabilidad/`** — cómo probar la observabilidad: logs estructurados (trace id, sin PII), métricas Prometheus/OpenMetrics (RED/USE, cardinalidad), trazas OpenTelemetry (propagación de contexto), healthchecks (liveness/readiness), error tracking, SLIs/SLOs y alertas. - **`pruebas-busqueda/`** — cómo probar búsqueda y relevancia (Elasticsearch/OpenSearch, Algolia, Solr, DB full-text): ranking y boosting, typos/fuzzy, sinónimos y stemming, facetas, cero-resultados, indexación, seguridad y golden set con métricas (precision@k, nDCG). Lo usa el `probador-busqueda`.
- **`pruebas-documentos/`** — cómo probar documentos generados (PDF/Excel/CSV): datos y cálculos, placeholders sin reemplazar, formato/locale, estructura y layout, metadata, seguridad (contraseña/firma) y accesibilidad del PDF. Lo usa el `probador-documentos`.
- **`pruebas-contenido/`** — cómo revisar contenido y typos en el idioma principal: ortografía y gramática, placeholders y claves de i18n a la vista, palabras duplicadas, Lorem ipsum, y consistencia de microcopy (distinto de las traducciones, que cubre el `analista-traductor`). - **`pruebas-mutacion/`** — cómo hacer mutation testing: medir la calidad de la suite de tests con mutantes, estados (killed/survived/no-coverage), mutation score, sobrevivientes vs. equivalentes, cómo acotar el costo (diff/módulo) y herramientas por lenguaje (Stryker, mutmut, PITest, Infection). Lo usa el `analista-mutacion`.
- **`automatizacion-k0lmena/`** — convenciones para generar automatización en k0lmena (`herramientas/k0lmena`): estructura web/api/mobile, nombres y tags, reutilización de steps, helpers, steps genéricos de API y validación con `npm`, más las plantillas de performance (k6, Artillery y JMeter). Incluye los steps de verificación en base de datos (que se agregan solo cuando se piden). Lo usan `web-mapper`, `api-mapper`, `mobile-mapper`, `performance-mapper` y `verificador-datos`.

## Cómo agregar uno

Creá una carpeta en `.claude/skills/` con un `SKILL.md` adentro:

```
.claude/skills/
└── mi-skill/
    ├── SKILL.md          # obligatorio: frontmatter (name, description) + instrucciones
    ├── references/       # opcional: detalle que se carga solo si hace falta
    └── scripts/          # opcional: scripts que el skill ejecuta
```

El `description` del frontmatter es lo que usa Claude Code para decidir cuándo cargar el skill. Más detalle en [`../../ARQUITECTURA.md`](../../ARQUITECTURA.md).
